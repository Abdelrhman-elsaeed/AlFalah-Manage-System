## Coverage and terminology

The owner requires one personal notification system covering conversations, School Duty, Student Affairs, manager approvals, dismissal completion, attendance recording, complaint submission/replies and relevant dashboard alerts. A top-bar bell exposes the authorized history and opens the correct work item.

In this package, **SchoolManager** means the manager of the affected school, not the global MainManager. **Authorized administrator** means an active school member with access to that particular feature and resource; SuperAdmin/global support access does not automatically subscribe someone to every school's alerts. A recipient must pass the same backend resource policy used by the destination screen, in addition to personal notification access.

Channels: every required event has a durable personal-center entry and foreground resynchronization; Web Push is available after N2 only on an opted-in, supported installation, subject to source eligibility and expiry. No push guarantee replaces a pending-work queue. Sender self-alerts, read receipts, typing indicators, page loads and ordinary counter refreshes do not create new device alerts.

## Common creation, noise and lifecycle rules

- Persist source transition, recipient center identity and delivery intent atomically (or use the existing durable business outbox). Never create a success notification before commit; channel retries never repeat business actions.
- Use a stable canonical key `(school, recipient, category, source, meaningful revision)`. Duty dashboard/System surfaces share it. Chat message identity remains authoritative for messages. Generic N1 invalidation/read events must never be promoted into phone alerts.
- Broadcast delivery is expanded only to currently eligible recipients. Avoid a global broadcast to all school accounts. Re-check current access before list/count/target resolution and before outbound attempts, including staff delegation, assigned teacher and guardian-link changes.
- Dashboard projections reuse the source event's entry. Snapshot counters do not each produce records; only a new actionable condition or meaningful revision does. Resolve/withdraw stale tasks without erasing audit history. The read/unread flag is independent of pending/resolved task state.
- Opening the bell does not mark its entire content read. Explicit read/read-all updates only the recipient's read state. Acknowledging a permit, approving a visit or closing a complaint requires the original authorized business action.
- A claim, provider acceptance, OS banner or read flag proves neither attendance execution nor acknowledgement. Retries may duplicate external banners; stable source identity limits duplicates without promising exactly-once delivery.
- Start new push eligibility from channel activation and current events; no historical/seed broadcast or mass conversion of Pending legacy records. Historical center access follows current source policy.
