# S1 — التنفيذ والتحقق وخطة الرجوع

**التاريخ:** 2026-10-03 · **النطاق:** S1 فقط. لا بدء لـ S2.

هذا تقرير S1 التاريخي. نُفذت S2 ثم S3 لاحقًا بتكليفين مستقلين؛ [تقرير S2](s2-library-and-uploads.md) و[تقرير S3](s3-evidence-and-review.md) يسجلان العقود والتحقق والقيود الحية. أدلة S1 محفوظة، والرايات مغلقة؛ S4 نُفذت لاحقًا بتكليف مستقل؛ [تقرير S4](s4-self-evaluation-and-reports.md) يوثق الجاهزية والتصدير والقيود والرجوع. S5 وS6 لم تبدأا.

## ما نُفّذ

- 11 جدولًا جديدًا: المجلدات، الأصول، النسخ، المتطلبات، الروابط، قرارات المراجعة، التفويض، عمليتا/أصول أرشفة الزيارة، ودفعات/صفوف الاستيراد. الأرشفة والاستيراد مخطط فقط؛ لا workers أو استيراد بروتوتايب أو ملفات جديدة على Drive.
- migration `20261003023752_SchoolFileStorageFoundation`: إنشاء وفهارس وقيود ومفاتيح فقط، وزرع 8 أذونات ومطابقتها للمدير/المعلم. لا تغيير في جداول المعلمين أو الشواهد أو حالات المصفوفة أو اتصال Google.
- Application services → repositories → SQL، وcontroller رفيع للتفويض يعيد `ApiResponse<T>`. خدمة الوصول الأساسية تفحص المدرسة والعضوية الحية والملكية والمنحة، ثم تستعمل حارس Drive الحالي؛ لا endpoints جديدة لعرض/تنزيل الملفات في S1.
- المنح والسحب للمدير الفعلي في `School.ManagerUserId` فقط، مع إذن DB وعضوية نشطة. لا وراثة امتياز تخزين من `Instructor.View/Edit` أو دور عام أو claims قديمة. التفويض التشغيلي مباشر، بمدة وسبب ومانح، ولا يمنح `Storage.Delegate`.
- منع تداخل فترات التفويض داخل transaction بمستوى Serializable؛ التعارض وrowversion القديم وSQL deadlock يعادون HTTP 409. سجل التدقيق والتفويض في المعاملة نفسها. السحب قابل للإعادة ويحتفظ بسبب المنح وسبب السحب منفصلين.

## القيود الفعلية في SQL Server

العلاقات بين الجداول الجديدة تستخدم مفاتيح مركبة `(SchoolId, Id)`. النسخة، والرابط، والقرار تستخدم `(SchoolId, StoredFileId, VersionId)` لمنع استعمال نسخة ملف آخر من المدرسة نفسها. FK مؤشر النسخة الحالية `(SchoolId, Id, CurrentVersionId)` أُضيف صراحة في migration: يبقى المؤشر scalar في نموذج EF لتجنب دورة استنتاج المفاتيح؛ لا يجوز إسقاط هذا القيد في migration لاحقة. فهارس المدرسة/المالك والمدرسة/DriveItem والمدرسة/السنة/المتطلب موجودة، و`rowversion` على السجلات الجديدة.

NULL يعالج بفهرسين فريدين للرابط النشط: أحدهما يحتوي `TeacherId` حيث `IsActive=1 AND TeacherId IS NOT NULL`، والثاني يستبعده من المفتاح حيث `IsActive=1 AND TeacherId IS NULL`. المتطلبات لها أربعة فهارس منفصلة لحالات المدرسة/السنة nullable، مع `TemplateVersion + Code` ضمن كل مفتاح. القالب لا يُربط كشاهد مباشرة: trigger يفرض مدرسة وسنة محددتين ومتطابقتين للمتطلب والرابط، ويحظر تغيير نطاق متطلب مرتبط.

Triggers تمنع دورات الشجرة، اختلاف مدرسة الزيارة عن عملية أرشفتها، وكتابة تاريخ القرارات أو هوية/بايتات النسخ أو provenance الموروث. تُسمح تغييرات توفر النسخة دون إعادة كتابة هويتها. مفاتيح المعلم القديمة تبقى بهوية المعلم وحدها؛ لا تربط تاريخ سنة ماضية بمدرسته الحالية بقيد مركب يمنع نقله. الوصول يعيد فحص ملف المعلم وعضويته ومدرسته الحالية في كل طلب. ملفات S1 الموروثة تحفظ SchoolId القديم بعد النقل.

## backfill ومطابقة البيانات

الأداة [StorageBackfill](../scripts/StorageBackfill/Program.cs) مستقلة عن تشغيل API، ولا تهيئ token service أو Drive client أو Data Protection أو seeder. الوضع مطلوب صراحة: `--dry-run` أو `--apply`. تخرج تقريرًا مجمعًا بلا أسماء ملفات/مستخدمين أو معرفات Google أو أسرار؛ exit 0 للمطابقة، 2 للاستثناءات/الانحراف، 1 لفشل التشغيل. تعليمات التشغيل في [scripts/README.md](../scripts/README.md).

كل submission صالح ينشئ أصلًا ونسخة تشير إلى **نفس** DriveId/DriveItemId. رابط واحد إلى المهمة الأصلية فقط عند وجود TaskId وAcademicYearId. قرارات Approved/Rejected تنقل بمراجعها ووقتها وملاحظتها؛ السجلات ناقصة السياق تصبح `NeedsLink` وتحفظ قرارها في provenance بلا شاهد أو مراجعة وهمية. IsDeleted وMissing والتواريخ وحالة الرفع محفوظة. نسخة Completed غير المفقودة تصبح **Unverified**؛ SHA256 وUploadedByUserId يبقيان NULL لأن السجل القديم لا يثبت البصمة أو المستخدم الذي رفع البايتات. لا تنزيل للبايتات لاستنتاجهما.

الحالة القديمة كاملة في `LegacyProvenanceJson`، مع مفتاح LegacySubmissionId فريد وبصمة snapshot. الإعادة لا تضاعف السجلات ولا تستبدل قرارًا محفوظًا. اختلاف legacy أو فقد بنية الهدف ينتج `LegacyOrTargetDrift`، ويحتاج تسوية قبل cutover. صف غير صالح يبقى في legacy ويظهر بمفتاحه وسبب الاستثناء في التقرير؛ تُحفظ الصفوف الصالحة معًا داخل معاملة، وفشل الكتابة يعيدها كلها. هذه أداة تحضير وليست مزامنة تشغيلية مستمرة؛ الشواهد القديمة تظل مصدر الحقيقة في S1.

تم إنشاء نسخة SQL معزولة باستخدام COPY_ONLY من Development؛ طُبّقت migration عليها وشُغّلت الأداة دون تشغيل API. لم تُطبق migration أو backfill على Development الأصلي أو production.

| القياس | dry-run | apply الأول | apply الثاني |
|---|---|---|---|
| submissions المصدر | 1 | 1 | 1 |
| ملفات/نسخ مخطط إنشاؤها أو منشأة | 1/1 | 1/1 | 0/0، موجود سابقًا 1 |
| روابط/قرارات | 1/1 | 1/1 | 0/0 |
| استثناءات | 0 | 0 | 0 |
| مجاميع الهدف بعد التطبيق | — | 1 أصل / 1 نسخة / 1 رابط / 1 قرار | المجاميع نفسها |

التقارير: [dry-run](s1-baseline-dry-run.json)، [apply 1](s1-baseline-apply-1.json)، [apply 2](s1-baseline-apply-2.json)، [سلامة البيانات](s1-data-safety.json). المقارنة تحتفظ بـ 1 submission Approved و1 منحة معلم؛ بصمة إعداد Google المشفر ثابتة في الأصل والنسخة، وصفر migrations للتخزين على الأصل وصفر عمليات Drive من backfill.

## التحقق

اختبارات الخدمة تغطي ملف المعلم مقابل زميله ومدرسة أخرى، سحب المنحة والتحرك خارجها، membership الحية، رفض تفويض متسلسل وclaims مزورة، تغيير المدير، نشاط الممنوح، الفترات المتداخلة والمنتهية، وسحب التفويض. اختبارات backfill تغطي dry-run وإعادتين، القرار القديم، deleted/missing، نقص المهمة/السنة، الاستثناءات والانحراف.

اختبارات SQL Server تُطبق السلسلة السابقة ثم S1 على قاعدة LocalDB جديدة ومعزولة. تفحص الفهارس nullable عمليًا، العلاقات والمدرسة والسنة وملكية النسخة، نقل المعلم مع بقاء التاريخ، الدورات والتاريخ append-only، rowversion وتدقيق السحب، السباق بين منحين، وفشل backfill قبل commit. اختبار DI يشمل خدمات التخزين الجديدة؛ أضيف IHostEnvironment إلى fixture الاختبار لأن الخدمة المحلية الحالية تتطلبه، دون تعديل خدمة مرفقات الطلاب.

النتيجة النهائية: **786 اختبار ناجح، صفر فشل وصفر تخطٍّ**، منها **41 للتخزين: 17 خدمة و24 SQL Server**؛ [ملخص النتائج](s1-tests.json). بناء API Release وأداة backfill: صفر أخطاء وصفر تحذيرات. EF لا يجد تغييرات نموذج معلقة، وفحص diff نظيف. أداة EF تعرض تحذيرات required-navigation/global query filters المعروفة؛ لذلك لا تُعامل قراءة child دون سياسة وصول قراءة مصرحًا بها. اختبارات الحذف والعزل والتاريخ تغطي مسارات S1 المستخدمة. TRX التفصيلي وقواعد الاختبار ونسخة SQL محفوظة محليًا تحت `.audit/sfs-s1` المستبعد من Git؛ التقارير المجردة فقط منشورة في هذا المجلد.

## rollout والرجوع ومصدر الحقيقة

القيم الافتراضية في `StorageOptions`:

```json
{
  "SchoolFileStorage": {
    "AdministrationEnabled": false,
    "ReadModelEnabled": false
  }
}
```

الأولى تغلق GET/POST/DELETE `/api/v1/storage/delegations` بـ404؛ الثانية محجوزة لتفعيل القراءة بعد التسوية في المرحلة المالكة، ولا توجد قارئات ملفات جديدة في S1 حتى لو غُيّرت. لا يُفعّل أي منهما هنا. rollback = إغلاق المفاتيح والعودة إلى المسارات القديمة مع إبقاء المخطط والبيانات والتاريخ؛ `Down` يرفض إسقاط جداول التخزين.

عند S2/S3، يلزم preview جديد في نافذة تمنع كتابات legacy المتزامنة، وتسوية drift والاستثناءات، ثم تكييف endpoints القديمة والجديدة إلى خدمة كتابة واحدة وسجل/روابط واحدة، ونقل قراءة المصفوفة إلى الروابط. لا يستمر مصدران مستقلان لقرار الاعتماد. أعِد اختبار حارس Drive والمجلدات المتداخلة والمعلم/المدير قبل أي cutover.

## القيود والتوقف

توجيه المالك الحالي أجاز تنفيذ S1 مع قيد S0؛ لم يتحول جدول parity إلى معتمد ضمنيًا. الاتصال الحي ما زال غير قابل لفك الاعتماد بالمفاتيح الحالية، ولم تتغير بياناته أو مفاتيح Data Protection. لذلك تحقق SQL والخدمات لا يثبت وجود الملف على Drive أو تشغيل الرفع/التصفح الحي. هذه بوابة تفعيل مؤجلة، لا عدد ملفات صفري أو اتصال ناجح. عينة Development ملف واحد؛ لا ادعاء بأداء آلاف العناصر. لم يبدأ S2 أو UI المكتبة أو مراجعات S3 أو جاهزية S4 أو أرشفة S5 أو استيراد S6.
